# Kolibri 1.1

[Blog post](https://aleph-alpha.com/en/blog/kolibri-1-1/) | [GGUF quantisations](https://huggingface.co/Aleph-Alpha/Kolibri-1.1-GGUF) | [Tech report (Kolibri 1)](https://aleph-alpha.com/downloads/tech-report.pdf)

Kolibri 1.1 is the successor to Kolibri 1, Aleph Alpha's mixture-of-experts
(MoE) reasoning model, with a focus on German and English. It adds sparse
attention for cheaper long contexts and improves on Kolibri 1 across several
capabilities. Like Kolibri 1, it supports an explicit reasoning mode and tool
calling.

## Intended use

Kolibri 1.1 is intended to process German and English text and to perform a
wide range of tasks beyond natural-language generation, for example multi-step
reasoning, coding, structured extraction, retrieval-augmented generation,
long-document processing and agentic tool calling.

Kolibri 1.1 has a native context length of 262,144 tokens. It can also process
contexts of up to 1,048,576 tokens (see Getting started), but quality on
complex tasks may decrease beyond the native length. We therefore recommend
contexts of at most 262,144 tokens.

For the kinds of systems Kolibri 1.1 is meant to be integrated into, see AI
system types below; for uses that we encourage users to refrain from, see
Responsible Use.

## Design goals

Kolibri 1.1 is designed to deliver strong German and English performance at low
serving cost. Its mixture-of-experts architecture activates only a small
fraction of its parameters for each token, keeping compute per token low while
retaining the capacity of a much larger model. The trade-off is memory: the
full model must be held in memory even though only part of it is active at any
time. To keep long contexts affordable, most attention layers focus on nearby
text, while a smaller number of layers select the parts of the whole context
most relevant to each token. We also developed a tokenizer tailored to German
word structure, so German text is processed efficiently without sacrificing
English. Supporting two languages rather than many is a deliberate choice of
depth over breadth.

## AI system types

Kolibri 1.1 is intended for integration into conversational assistants and
agentic workflows in German and English, in which a person reviews the model's
output before it is acted on rather than autonomous systems that act
unreviewed. It suits document-processing and drafting systems,
question-answering systems over an organisation's own material, and internal
knowledge and research tools. Its tool-calling and structured-output
capabilities make it appropriate for orchestration layers that call APIs,
execute code, or run searches, provided the calling system validates the
results. In decision-support systems it belongs on the advisory side, surfacing
evidence and drafting options for a human to weigh, and it is not intended as
the deciding component. More broadly, it is built for human-AI collaboration
rather than unsupervised operation.

## Sustainability

### Energy consumption

9.88×10² MWh (estimated), including node power and data-centre overhead (PUE).
This includes pre-training, mid-training and long-context training, SFT and RL.
Of this, 8.82×10² MWh was used up to and including dense mid-training
(inherited from Kolibri 1), and 1.06×10² MWh from sparse mid-training onwards.
It excludes peak, idle and low-load states, and proxy and ablation models.

### Energy measurement

For pre-training, we obtained the average power usage per node and the power
usage effectiveness (PUE) from the cluster provider. We multiplied these by the
number of nodes and the runtime to obtain a total energy estimate.

## Getting started

We provide multiple options to run Kolibri 1.1: our official vLLM plugin and
our GGUF quantizations with llama.cpp. The official evals we publish in this
model card only hold for the unquantized model served with vLLM.

### Serving with vLLM

Kolibri requires the **aleph-alpha-inference** package that provides the
Kolibri vLLM plugin. You can either use the provided container image
`ghcr.io/aleph-alpha/aleph-alpha-inference`, or install the package from
[Aleph-Alpha/aleph-alpha-inference](https://github.com/Aleph-Alpha/aleph-alpha-inference),
which also installs the vLLM version it supports:

```bash
pip install 'aleph-alpha-inference>=2'
```

Serve the model with reasoning and tool-calling enabled:

```bash
vllm serve Aleph-Alpha/Kolibri-1.1 \
  --reasoning-parser kolibri1 \
  --tool-call-parser kolibri1 \
  --enable-auto-tool-choice
```

To serve contexts beyond 262,144 tokens, add `--max-model-len 1048576
--hf-overrides '{"max_position_embeddings": 1048576}'`.

The recommended sampling parameters for the model are `temperature=1.0`,
`top_p=0.99` and `top_k=128`.

#### Querying the server (OpenAI-compatible API)

```py
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

response = client.chat.completions.create(
    model="Aleph-Alpha/Kolibri-1.1",
    messages=[
        {
            "role": "user",
            "content": "Erkläre kurz, was ein Mixture-of-Experts-Modell ist.",
        },
    ],
    extra_body={
        "chat_template_kwargs": {
            "reasoning_effort": "high",
            "enable_thinking": True,
        }
    },
)
print(response.choices[0].message.content)
```

#### Reasoning mode

Kolibri 1.1 supports explicit thinking effort levels that need to be configured
through the chat template. You can pass `reasoning_effort` values `low`,
`medium` and `high` to configure the amount of effort our model puts into
finding the answer. You can disable thinking altogether by setting
`reasoning_effort` to `none` or passing `enable_thinking=false`. The model then
responds immediately.

#### Tool calling

The serving command enables Hermes-style tool calling (`--tool-call-parser
kolibri1 --enable-auto-tool-choice`). Pass your function schemas via the
standard `tools` field of the chat completions request; the model will emit
tool calls that the parser converts into structured output. Tool calling can be
combined with reasoning mode.

```py
import json
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
MODEL = "Aleph-Alpha/Kolibri-1.1"

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a city.",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "City name, e.g. Heidelberg",
                    },
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]},
                },
                "required": ["city"],
            },
        },
    }
]


def get_weather(city, unit="celsius"):
    return {"city": city, "temperature": 18, "unit": unit, "conditions": "cloudy"}


messages = [{"role": "user", "content": "Wie ist das Wetter gerade in Heidelberg?"}]

first = client.chat.completions.create(model=MODEL, messages=messages, tools=tools)
msg = first.choices[0].message
messages.append(msg)

for call in msg.tool_calls or []:
    args = json.loads(call.function.arguments)
    result = get_weather(**args)
    messages.append(
        {
            "role": "tool",
            "tool_call_id": call.id,
            "content": json.dumps(result),
        }
    )

final = client.chat.completions.create(model=MODEL, messages=messages, tools=tools)
print(final.choices[0].message.content)
```

**Setup.** All models are compared on the same evaluation setup, with identical
prompts, few-shot configurations and task settings. Most benchmarks run in
[eval-framework](https://github.com/Aleph-Alpha-Research/eval-framework/),
TerminalBench and SWE-Bench in
[Harbor](https://github.com/harbor-framework/harbor). Each model uses its
documented context window and sampling parameters and runs at its highest
reasoning setting, i.e. the highest reasoning effort or thinking enabled.
Qwen3-Coder-Next has no reasoning mode. A model reports no score (–) when it
cannot perform a certain task or when a prompt or agent trajectory exceeds its
context window.

**Averages.** _Overall_ is the mean of _Overall (EN)_ and _Overall (DE)_, so
both languages count equally. Each of those is the mean of its language's
category averages. A category average covers only the benchmarks where every
model gets a valid score; the excluded benchmarks are greyed out. AA-Omniscience Index is excluded
as well, since its constituents AA-Omniscience Accuracy and Hallucination Rate
are already included. Lower-is-better rates (↓) are inverted, i.e. counted as
100 − rate. SealQA counts as one benchmark, scored over all its questions, with
its two distractor settings reported separately in greyed out rows. Honeypot
(EN/DE) is bilingual and counts towards both EN and DE averages. Average scores
are not directly comparable across categories and languages.

### Pre-training

We branched from the Kolibri 1 mid-training checkpoint at step 34,000, after
3.42T of the original 3.44T mid-training token horizon. We converted its
attention to shared-KV sparse attention, where each query attends to 2,048
selected keys and several layers reuse the keys and values of an earlier layer.
We then continued with a second mid-training phase and a long-context phase.

The second mid-training phase increased the sequence length to 196,608 tokens
and used a global batch size of 512 sequences. This keeps the 100.67 million
tokens per step of the original 65,536 × 1,536 mid-training batch. The second
mid-training had 805-billion-token budget corresponding to 8,000 optimisation
steps. The converted checkpoint was loaded without optimizer state, so this
phase used a learning-rate warmup of 50 steps.

The subsequent long-context phase increased the sequence length to 262,144
tokens and used a global batch size of 768 sequences, corresponding to 201.327
million tokens per step. Its 201-billion-token budget corresponds to 1,000
optimisation steps. It resumed the optimizer state of the mid-training phase
and used no additional warmup.

Both phases saved a checkpoint every 25.2 billion tokens, giving 32
mid-training and 8 long-context checkpoints. The final model is a uniform
average of all 40 of them, covering the full 1.0 trillion tokens of both
phases.

Mid-training ran on 512 GPUs and long-context training on 384 GPUs, using our
PyTorch-based TorchTitan distributed training infrastructure. Training used
bfloat16 parameters, float32 reductions, and a maximum gradient norm of 10.0.

**Pre-training and mid-training data mix**

Kolibri 1.1 uses the training data, synthetic data and data curation pipeline
of Kolibri 1, including its URL filtering, heuristic filtering, deduplication,
quality classification, PII redaction, harmful-content filtering and
decontamination. The [Kolibri 1 technical
report](https://aleph-alpha.com/downloads/tech-report.pdf) and the [Kolibri 1
model card](https://huggingface.co/Aleph-Alpha/Kolibri-1) describe them in
detail. Below, we summarise the measures against harmful content and bias,
followed by the only new data in Kolibri 1.1.

**Harmful and unsuitable content.** Illegal, harmful, unethical and infringing
sources were excluded through the URL-level filtering, which also removed known
adult and NSFW sites. For English web data, keyword-based filtering
additionally removed sexually explicit content. These measures also address
child sexual abuse material (CSAM). Personal data was redacted with placeholder
tokens. The training corpus was text-only, so image-based CSAM or
non-consensual intimate imagery (NCII) was not ingested.

**Bias mitigation.** German is under-represented in web content, which lowers
German performance. Kolibri 1 counteracted this by upsampling German data where
downstream evaluations showed gains, and by adding translated and synthetically
rephrased German data to diversify style and register. The second mid-training
phase of Kolibri 1.1 raised the share of German web and document data from 2.1%
to 14.5% (see the table below). Openly available fine-tuning data is often
generated by models that carry political bias; we built a dedicated
post-training dataset to counteract risk of contamination of our training data
with politically biased material, grounded in curated reference material on
politically sensitive topics.

The only new data is the mix of the second mid-training phase. It draws on the
same Kolibri 1 mid-training and pre-training data, reweighted towards
natural-language web and document data, especially German.

### Post-training

Post-training was split into two phases: A supervised fine-tuning stage that
instilled reasoning and instruction-following capabilities and a reinforcement
learning stage that trained the model across a broad set of environments.
Across both stages, we put particular focus on the key capabilities that shape
the strengths of Kolibri.

#### Capabilities

**German.** We trained our model to reason in German to make it easier for our
users to follow along. For SFT, we generated translated prompts across a wide
range of domains, generated language consistent reasoning answers, and filtered
the answers for correctness and language consistency. We continued this
training in RL, where we used German environments and included a language
consistency reward for both the reasoning trace and the answer.

**Reasoning Effort.** Kolibri 1.1 can answer directly (reasoning effort `none`)
or reason at `low`, `medium` or `high` reasoning effort, which the chat
template requests through a fixed sentence in the system prompt. In SFT, we
assigned reasoning effort labels based on observed dataset-specific reasoning
length statistics and judged difficulty. In RL, we trained each task across all
reasoning levels with effort-specific length penalties.

**Safety.** Kolibri 1.1 was trained in SFT to decline harmful and illegal
requests while still providing partial answers where appropriate. Additionally,
we added training data in which instructions are injected into documents and
tool results, so that the model follows the user’s request rather than the
injected text. These safeguards do not replace safeguards in the application,
such as content filtering and output validation.

**Personally Identifiable Information.** In addition to the mitigations during
pre-training, our SFT mix contains examples that refuse PII extraction
attempts. Our safety evaluations measure these refusals.

**Long Context.** We trained Kolibri 1.1 on context windows up to 262k tokens,
which enables reasoning over large documents. Since most datasets usually focus
on short-context, we curated datasets that contained long-context documents
based on publicly available data (e.g., from German legislative documents) with
corresponding question/answering prompts. We also trained on long-context
question-answer during RL.

**Agentic Use and Tool Calling.** We trained Kolibri 1.1 to perform well in
agentic settings involving tool calls and terminal interactions. For
permissively available agentic SFT datasets, we regenerated the reasoning
traces. During training, we masked out erroneous tool calls and terminal
actions, so the model learned to recover from errors without learning the
erroneous actions themselves. In addition to such permissively available data,
we generated additional software-engineering SFT datasets. During the RL stage,
we trained on multiple tool-calling, software-engineering and terminal
environments and randomised the harnesses to support generalisation.

**Retrieval.** To make our model suited for customer information retrieval
use-cases, we built environments that cover retrieval-augmented question
answering over German and English corpora across general knowledge and
specialised domains such as legal, electronics, hardware and aviation. The
environments were heavily randomised across different harnesses, retrieval
parameters, and languages. To warm-start the RL training phase, we generated a
curated set of high-reward completions for SFT training.

**Hallucinations.** To address hallucinations, we trained with abstention data.
We also constructed RL environments that implement our [Merlin-Arthur
protocol](https://arxiv.org/abs/2512.11614). The protocol shows the model each
question with parts of the context hidden. One player, Merlin, hides parts such
that the probability of the ground-truth answer increases; we trained the model
to answer Merlin examples correctly. The other, Morgana, hides parts of the
context which decreases the probability of the correct answer, and we trained
the model to abstain on Morgana samples. We also trained on the original,
unmasked samples. To warm-start the RL training, we generated Merlin-Arthur
rollouts for SFT and filtered out low-reward rollouts.

**Visual Output.** We trained Kolibri 1.1 on text-data to write code that
renders to visual output, such as SVG graphics, HTML animations, TikZ figures,
CAD models, Blender scenes and PowerPoint slides. For SFT, we generated
reasoning traces for these tasks. During RL, we trained on environments that
render the model’s output and score it against a reference.

#### Supervised Fine-Tuning (SFT)

We fine-tuned three models for 5,000 steps with a global batch size of 256
sequences of 262,144 tokens, about 336 billion tokens per model in total. We
kept the optimizer split of pre-training, Muon for the two-dimensional backbone
parameters and AdamW for everything else, and configured it at a quarter the
pre-training learning rates. The learning rate warmed up over 50 steps and then
followed a cosine decay to a tenth of its peak over the remaining steps.

**Data Selection and Curation.** We used permissively available datasets as
well as in-house generated data. We unified and aligned all datasets and
decontaminated w.r.t. evaluation datasets. We filtered all of our data for
political bias potentially inherited from generator models. In addition, we
generated data centred on human dignity, universal human rights, liberal
democracy, the rule of law and pluralism.

**Mix Weighting.** Similar to Kolibri 1, we determined the relative weighting
of our SFT data mix with a model-merging approach, drawing on ideas from prior
work such as [MergeMix](https://arxiv.org/abs/2601.17858). We split our mix
into 29 data clusters. We trained one specialist per cluster on 3.5B packed
tokens, merged 88 weightings drawn from Dirichlet distributions around our
hand-tuned mix, and scored every merge on 21 benchmarks in eight capabilities.
A Bayesian optimization proposed new merged weightings which we ablated in
short 13.4B token target scale runs. Based on these results, we chose the data
mix candidates for full scale training.

**Model Souping.** To produce the final checkpoint, we merged three checkpoints
trained for the same token horizon on two different data mixtures. Their
respective strengths carried over into the final model.

#### Reinforcement Learning (RL)

We trained in an asynchronous reinforcement learning setup, where vLLM
inference ran in parallel to training. Updated model weights were synchronised
to the inference engine without waiting for ongoing generations to finish. We
kept the optimizer of the SFT stage but adapted its learning rate, and used
quantization-aware training to enable efficient low-precision inference with
vLLM.

We trained for a total of 650 steps with a total batch size of 4,096 and a
maximum sequence length of 262k tokens across all environments simultaneously.
Most environments use verifiable rewards for the verification, while a few
open-ended ones are scored by an LLM-as-a-Judge instead. Every environment
additionally includes format rewards to encourage general style and
consistency. All tasks are heavily randomised over different harnesses, system
prompts and languages to encourage generalisation. For hard tasks that the
model cannot solve, we additionally used on-policy self-distillation to hint
the model towards the correct solutions.

## Risks and limitations

**Note:** The use of language models in high-stakes environments, for critical
decisions or to support a user's wellbeing should be performed with additional
guardrails in place. All use of our model as part of a downstream AI system
must meet all applicable regulatory and legal requirements, especially
Regulation (EU) 2024/1689 (EU AI Act).

In the following sections, we describe risk categories and steps to minimize
these risks.

### Harmful Language

Large language models can sometimes generate undesired outputs that are
unsuitable for certain applications. This includes producing content with
harmful language, discriminatory content, inappropriate tone and style, or
systemic biases. Our model has also not been optimised to represent a political
opinion or take a specific point of view, and may generate outputs that
contradict a user's opinion or expectation, including hateful or violent
content. Such outputs can also include incorrect, outdated information, or
material that is not suitable for all ages. While we constantly take efforts to
reduce the likelihood of such undesired outputs, this possibility can never be
fully ruled out. To minimise these issues, the following strategies can be
employed:

- Abide by the guidance on Responsible Use provided for in this Model Card.
- Crafting prompts carefully to guide the model's output more effectively.
- Conducting additional validations at the application level to ensure output
  quality and appropriateness, e.g. via Red-Teaming or classifying the output.

### Systemic Biases

Language models obtain world knowledge from their pre-training data and may
therefore exhibit the same systemic biases that are present in the data.
Differing deployment scenarios (including differing cultural contexts) can
expose systematic biases in different ways. We acknowledge the cultural
diversity of communities and users worldwide.

### Outdated World Knowledge

Our model's implicit knowledge reflects its pre-training data cutoff (EN/DE
June 18, 2026). Pre-training uses a fixed dataset compiled at a fixed point in
the past, so the model's world knowledge is limited to what that data
contained. This means more recent events or facts may be unknown to it, or
misunderstood if presented as input during live usage. This mainly matters for
deployments without internet or tool access, since the model will otherwise use
tool calling to work around potentially outdated information.

Risks include:

- Generation of unintended, irrelevant, or repetitive outputs. This includes
  the production of incorrect or outdated information.

Risks may be mitigated by:

- Injecting context, where relevant.
- Crafting prompts carefully to guide the model's output more effectively.
- Performing validations on the application layer, e.g., classifying the
  output.
- Using a repetition penalty or other parameters available in the API (see
  [vLLM
  documentation](https://docs.vllm.ai/en/v0.33.0/api/vllm/sampling_params/)).

### Political Bias

We acknowledge the diversity of political contexts our model can be used in.
Our model is not optimised to have a consistent political position across a
large variety of political topics and may reproduce political biases present in
its training data in some contexts.

Our model's training data also contains material generated with Chinese
language models that are known to carry bias towards certain political
positions (see [blog
post](https://aleph-alpha.com/en/blog/training-on-the-party-line/)). We
actively reduced this type of political bias in our model, including through
data filtering and dedicated alignment training.

### Prompt Injection

AI models can receive instructions that try to change their behaviour: users
may paste text that contains them or attackers hide them in documents, web
pages and tool results. We trained Kolibri 1.1 to follow the user’s request,
within the system prompt’s rules, rather than such injected instructions, but
this does not prevent every attack. Keep confidential data, like credentials,
out of the system prompt, treat external content as untrusted, give tools only
the permissions the task needs, and have a person confirm actions with side
effects.

### Mistaken for a Human

Users may attribute human traits to AI models. This also includes the fact that
content generated by the model is not in any case explicitly detectable at this
point. It is therefore required to design the system in a way that mitigates
the impact of unintended interpretation and especially adhere to applicable
transparency requirements.

### Other Errors

Any AI model can produce errors, even after implementing all legally required
and additionally recommended measures. When integrating foundation language
models into an application, users should:

- Be aware of the risk of (harmful) failure cases and implement the use case in
  a way that mitigates such risks.
- Be aware that foundation models do not contain application logic, e.g.,
  content filters. Enforcement policies relevant to the use case need to be
  implemented in the application layer.
- Avoid unsupervised and unverified use in high-stakes environments.
- Validate output with adequate measures.

### Reproducibility

Some inference parameters, e.g., temperature, lead to the random sampling of
outputs, which precludes the reproducibility of outputs. Even when such
parameters are not in use, outputs may diverge slightly on a numeric level for
technical reasons. One may implement the following measures if needed:

- Logging of past model outputs on the application layer (Aleph Alpha is not
  storing any data and/or using any data provided in prompts for the training
  of its LLMs).

This list of risks, biases, and limitations may not be complete, as improving
the understanding and behaviour of language models is an ongoing research topic
in the AI science community.
